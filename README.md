# 🐱 Cat Client

**Cat Client** is a powerful Android VPN client built on the Mihomo core,
combining one-tap connectivity with all the tools Iranian users need.

## ✨ Features

- 🎨 **Purple / black / white UI** — the whole app (and the panel) runs on the violet
  palette: light = white surfaces with Cat purple, dark = pure-black OLED with
  violet/fuchsia gradients, plus system-theme + accent pickers
- 🐱 **Icon**: white cat with a violet lightning bolt on a purple-night
  gradient (regenerated by `scripts/branding/generate-icons.py`)

## ⚡ Deploy your own Cat Panel — one click, no app needed

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/mazodimobinhost-creator/cat-client)

> 🔐 **SOCKS5 relays and credentials.** A relay is stored as `socks5://user:pass@host:port`
> inside the panel's own settings, which live in the **Cloudflare KV namespace bound as `CAT_KV`**
> (key `cat_settings_v1`, alongside users and the clean-IP list). So:
> - the password is **saved in your KV exactly as you type it** — it is not hashed or encrypted there,
>   because the worker must present it to the relay on every handshake;
> - it is **masked everywhere it is displayed**: the SOCKS5 list shows `socks5://***@host:port`, and
>   `maskCreds()` strips credentials from anything written to the in-panel error log;
> - it is **never sent to any third party** — the worker dials the relay itself, and the subscription
>   links carry the relay only as part of your own worker's address.
> If you do not want a password sitting in KV, run the relay without authentication (or with an
> IP allowlist) and add it as `socks5://host:port`.

> 🔄 **Action required after this update — and a behaviour to expect.**
> 1. **Every user must re-fetch their subscription.** Links no longer carry the relay address, only
>    a server-side id, so links fetched before the update keep pointing at the old reference and
>    will stop working. Ask your users to re-import / update their subscription.
> 2. **Removing a relay breaks the configs that referenced it.** The worker refuses those
>    connections (WebSocket close `1008 relay unavailable`) instead of dialing the target directly —
>    failing open would have kept the user browsing while silently dropping the relay they asked
>    for. Add the replacement relay first, let users re-fetch, then remove the old one.

**The credentials never travel in a subscription.** Older builds put the whole relay URL into every
config as `?proxyip=socks5://user:pass@host:port`, which published the password to anyone who saw
the link (and wrote it into client logs). Now a link carries only an opaque reference,
`?proxyip=relay:<16-hex-id>`, and the worker resolves that id back to the real relay from its own
settings (KV) at dial time — the URL itself never leaves the worker. Two consequences worth knowing:
the relay's **address** (`host:port`) still appears as the config's display name, the same way any
server address does; and if you **remove a relay from the panel**, links carrying its id stop
resolving — they fail closed instead of dialing something else.

> 📦 The button deploys the **committed stealth build** (`dist-panel/catpanel.stealth.js`) — the only artifact with **no plaintext panel fingerprint at all**: regex literals, object keys, member properties and short-hands are rewritten to concatenations, the string table is rc4-encrypted, and there is no version-marker line. Cost: ~604 KB gzipped and the deployed code is not human-auditable. The readable `dist-panel/catpanel.min.js` (120 KB gzipped, carries the version marker) is still built and committed — point `main` back at it in `wrangler.jsonc` for an auditable deploy. CI rebuilds it from the AGPL source at `app/src/main/assets/panels/catclient.worker.js` on every push — and because the rc4 string table is salted with fresh noise each run, **the stealth file's bytes (and its md5) change on every rebuild** while `catpanel.min.js` stays byte-stable. Pin a commit when you quote an md5: `https://raw.githubusercontent.com/mazodimobinhost-creator/cat-client/<commit>/dist-panel/catpanel.stealth.js`.
>
> ⚠️ **Hypothesis, not a documented fact.** The obfuscated snapshot (`dist-panel/catpanel.obf.js`) was added on the belief that *"Cloudflare statically scans deployed worker sources for `vless`/`trojan` signatures and disables the worker with Error 1101"*. That belief could **not** be confirmed: Cloudflare's own documentation defines **1101 as "Worker threw a JavaScript exception"** — a runtime failure (uncaught exception, CPU/memory limit, crash in the global scope) — and the scanning story traces back only to community reports from November 2024, never to a Cloudflare statement. So it is recorded here as a **hypothesis**, and the deploy path no longer pays its price (533 KB gzipped, ~4.4× heavier, and unauditable). If you have a deployment that was disabled with 1101 and a Cloudflare ticket or log showing a source scan, open an issue — that would turn this from a hypothesis into a fact. The obfuscated snapshot is still built for the in-app updater, but it is **not** deployed.

### 🔗 دیپلوی خودکار با Cloudflare Workers Builds (اتصال به گیت‌هاب)

به‌جای پیست دستی: کلادفلر به مخزن وصل می‌شود و با هر push روی شاخهٔ انتخابی، خودش
`wrangler deploy` را اجرا می‌کند. هر چه لازم است از قبل در مخزن هست —
`wrangler.jsonc` (ورودیِ `dist-panel/catpanel.stealth.js` + بایندینگِ `CAT_KV`) و CIیی که همان
فایل را از سورسِ AGPL می‌سازد (`scripts/panels/stealth.mjs`).

**۱) KV — یک‌بار. و بله، `CAT_KV` در `wrangler.jsonc` تعریف شده است** (خطِ
`"kv_namespaces": [{ "binding": "CAT_KV" }]`). این مهم است چون دیپلوی **declarative** است:
لیستِ بایندینگ‌های نسخهٔ آپلودی مو‌به‌مو همان چیزی است که آن فایل می‌گوید، پس هر KV/متغیری که در
داشبورد باشد و در فایل نباشد، با `wrangler deploy` **حذف می‌شود**. اگر بایندینگِ دیگری در داشبورد
دارید (مثلاً یک KV با نامِ دیگر) قبل از وصل‌کردن Builds اسمش را هم داخل همین فایل اضافه کنید.
کانفیگِ فعلی فقط `CAT_KV` + `OPEN_PANEL`/`OPEN_SUB` را می‌فرستد و تست
(`scripts/panels/wrangler-config.test.mjs`) گارد می‌کند که بایندینگِ ناشناس یا نوعِ دیگری (D1/R2/…)
بی‌سروصدا اضافه نشود.

اگر ورکرِ فعلی از قبل با نامِ `CAT_KV` به یک namespace وصل است، کاری لازم نیست: بایندینگ بدونِ `id`
می‌ماند و Wrangler همان namespace را نگه می‌دارد (automatic provisioning — مستنداتِ کلادفلر؛ در
wrangler 4.135+ بایندینگِ بدون `id` با نام تطبیق داده می‌شود). برای قطعیتِ صد‌درصدی:
**از موبایل** داشبورد → *Storage & Databases* → *KV* → روی namespace بزنید → فیلد **ID** (۳۲ کاراکتر
هگز) را کپی کنید → در گیت‌هاب فایل `wrangler.jsonc` را باز کنید → خطِ کامنت‌شدهٔ
`// "id": "0123456789abcdef0123456789abcdef",` را از کامنت دربیاورید و ID را جایش بگذارید → Commit.
**هیچ‌وقت idِ ساختگی نگذارید** — ورودیِ فعالِ نامعتبر، دیپلوی را می‌شکند.
بعد از دیپلوی، صحتش را با این بسنجید: `https://<your-worker>/api/diag` (مالک) باید
`"kv":"read+write ok"` بدهد و `/api/settings` باید همان آی‌پی‌ها/کاربرهای قبلی را نشان بدهد.

**۲) وصل کردن مخزن — روی موبایل، ضربه‌به‌ضربه.** (اگر آیتمی را ندیدید، در مرورگرِ گوشی منوی
«⋮» → **Desktop site** را روشن کنید؛ رابطِ موبایلِ کلادفلر بعضی زیرمنوها را پنهان می‌کند.)

2. منوی **☰** (بالا-چپ) → **Workers & Pages**.

## 🛠️ Build

Requirements: JDK 21, Android SDK (platform 36, build-tools 35.0.0, NDK 29, CMake 3.22.1), Go 1.24+.

```bash
./scripts/build-flclash-core.sh     # builds Mihomo native core for all ABIs
./gradlew assembleDebug             # debug APK at app/build/outputs/apk/debug/
```

The easiest path is to push to this repo — GitHub Actions builds debug + release APKs automatically and attaches them to a versioned release.

## 🖥️ Windows app

The desktop build lives in [`windows/`](windows/README.md) — a dependency-free
tkinter client with the same Cat identity (subscriptions + copy in every
format + share with multiple users, clean-IP scanner with real country flags,
free configs and link latency tests). Run `windows/run.bat`, or download the
`CatClient-Windows.zip` asset from a GitHub Release (built by GitHub Actions
with PyInstaller). Windows builds run in the dedicated `windows` workflow.

## 🔄 In-app updates

Cat Client includes an **App updates** card under Settings. It checks the official Cat Client GitHub release, chooses the APK matching the installed ABI, downloads it through Android DownloadManager, verifies the release `SHA256SUMS`, package name, version code, native ABI set and signing certificate, then opens Android's installer. The app never installs an arbitrary URL or a mismatched APK.

For upgrade-in-place updates, configure the stable release-signing secrets described in [docs/release-signing.md](docs/release-signing.md). APKs made with the temporary CI fallback key are for smoke testing and require a one-time uninstall before migrating to the stable-key release.

## ☁️ Cat Panel updates from inside the app

The Cloud tab's **My Cat Panel deployments** card shows the live version of every panel you deployed. **Update panel** pulls the newest official panel source (the GitHub release asset, falling back to the copy bundled in the APK) and re-uploads it to the same Worker — your UUID password, subscription links, users, quotas and saved settings survive untouched. Readable bindings are carried over; if the Worker holds hand-made secrets the API can never return (like `PANEL_PASSWORD`), the update stops safely and tells you to update from the Cloudflare dashboard instead. When a deployment is already current, the same button reinstalls/repairs the worker.

## 🐱 Cat Panel (built-in Cloudflare Worker)

`app/src/main/assets/panels/catclient.worker.js` is the whole panel — one file (~145 KB).

   Worker* → paste the file → Deploy → add a KV namespace binding named `CAT_KV`

   sign in: the password **is the UUID** until you change it in settings.
2. **Through Cat Client** — Cloud tab → paste an API token → *Deploy on my
   Cloudflare*. The app creates the KV, uploads the worker, and imports the sub.
   The *copy Worker code* button next to it fills the clipboard with this same
   3-line `catpanel.min.js` (474 KB) for a manual paste — never the ~1.2 MB bundle
   the app uploads through the API, because a 1.2 MB clipboard string is the
   classic route to a truncated paste (→ «Error 1101», see below).

### ⚠️ «Error 1101» — how to tell «the script never loaded» from «a request threw»

**The guard added in 6.66.6+ is not a promise that 1101 can never appear.** It turns
*request-time exceptions* into JSON; three other things still produce Cloudflare's
page, by construction, because no code of ours runs in those cases:

| What happened | Who catches it | What you see |
| --- | --- | --- |
| an exception **inside `fetch()`** on this request | the outer `try/catch` | JSON report (owner) / generic JSON for `/api` (stranger) — never the 1101 page |
| the file **never evaluated**: syntax error, truncated paste, a throw in **global scope** during module evaluation | *nobody* — the module did not load | **1101 on every route**, forever, until you redeploy |
| Cloudflare **refused the upload** (validation error, size, invalid binding), or the deploy never reached the account | *nobody* — nothing was deployed | usually a deploy error in the dashboard/build log; the old version keeps serving, or 1101 if the previous upload was broken |
| a **fatal runtime kill**: out of memory, or the isolate killed mid-request | *nobody* — the isolate dies | the 1101 page (1102 for CPU-time limits) |

So the first question is still which of these you have:

| Open `https://<your-worker>/api/version` | Meaning | Fix |
| --- | --- | --- |
| JSON: `{"ok":true,"panel":"cat-panel","version":"…"}` | the script is **loaded and running**; something a *request* did threw | open `/api/diag` (owner) or set `PANEL_DIAG=1`, then read the JSON report |
| the 1101 page (or any non-JSON) | the script **never loaded** — truncated paste, half-copied file, a bad build, or a deploy that did not land | deploy again from a verified file (below) |

The app answers the same question for you: after every deploy/update it asks
`/api/version` and says which of the three situations you are in — JSON back (the
panel is online, with its version), *the edge answered but our code never ran*
(HTTP status + the edge's first 120 characters, i.e. the 1101 that has no report)
or *no answer at all* — together with a warning when the panel on the Worker and
the panel inside the app disagree. It also sends the panel URL with
`av=<app version>&pv=<panel the app ships>` so the panel raises the same warning
from its own side, and its uploader now sends the multipart body with an exact
`Content-Length` — a short write can no longer be stored as half a module, which
is one of the ways a Worker ends up answering 1101 for every request.

What the app uploads, measured (6.67.0): the APK asset
`panels/catclient.worker.js` is the **obfuscated** bundle (CI replaces the readable
source in place with `obfuscate.mjs`), 1,250,472 B, sent as
`main_module=worker.js` with `compatibility_date 2025-03-04` +
`compatibility_flags: ["nodejs_compat"]` and the `UUID`/`PANEL_USER`/
`PANEL_PASSWORD`/`CAT_KV` bindings. Replayed on the real Workers engine (workerd)
with those exact settings, that bundle boots and answers `/api/version` 200 JSON,
`/health` 200 and `/panel` 200 — so the file is not the cause of a 1101 on a
Worker this flow created.

A file that never loads cannot report anything. So before pasting, look at the first
line (`/* CAT_PANEL_VERSION = '6.67.0' */`), the last characters
(`…userInfoPage:Xa,camouflagePage:Ka};` for `catpanel.min.js` in this release) and
the size (494,032 bytes — gzip 138,407 B, under the 150 KB budget). The browser's editor wraps the three long lines, so «it
looks like two lines» means nothing; the byte count is what matters.

Since 6.66.6 (shape finalised in 6.66.7) a request-time exception answers JSON for
the owner instead of the 1101 page. **You can prove it on your own Worker** — the
owner-only self-test throws on purpose:

```bash
# signed in (or x-cat-key: <panel password / UUID>) — this one always answers:
curl -s https://<your-worker>/api/selfcheck            # {"ok":true,"version":"6.67.0","handler":"alive …"}
# and this one throws inside the Worker, so you see the report, not a 1101 page:
curl -s "https://<your-worker>/api/selfcheck?throw=1" | head -c 400
```

The second command returning `error:"panel_crash"` with a `stack` — instead of
Cloudflare's «Error 1101: Worker threw exception» page — is the whole test. A
stranger asking for the same URL is refused with `401` before the throw, so nobody
can use it to force a report out of your panel.

**Who sees the stack.** The full report (message + `stack` + path) goes to the owner
only: a valid session cookie, `x-cat-key: <panel password / UUID>`, the `?p=<uuid>`
one-tap login, or `PANEL_DIAG=1`. Everyone else gets a generic
`{"ok":false,"success":false,"error":"internal","message":"unhandled error"}` — no
message, no stack, no path, no version, not even the `panel_crash` marker, and the
same for the HTML routes (the neutral page). The one deliberate exception is a
**fresh install with no password anywhere**: there is no owner to prove yet, and the
panel path already shows the UUID to whoever opens it, so the report is not a new
disclosure there — set a password (or `PANEL_DIAG=0`) to close it. Pinned by
`scripts/panels/hostile-env.test.mjs` (86 checks: every audience, both switches).

The report itself:

```json
{"ok":false,"success":false,"error":"panel_crash","title":"Worker Exception Handled",
 "version":"6.66.7","at":"/panel","method":"GET","message":"…",
 "stack":"Error: …\n    at …","stackLines":["Error: …","    at …"],
 "recent":[{"t":0,"k":"unhandled","stack":"…"}],"hint":"This replaced Cloudflare's «Error 1101» page. …"}
```

What that promise does and does not cover — worth knowing before you chase a 1101:

| Situation | What you get |
| --- | --- |
| anything thrown inside `fetch()` — including a thrown string, `null`, or a hostile object whose `message`/`toString` throws | JSON report above (`env = env || {}` is set before the `try`, and every value in the error path goes through `safeText()`/`safeStack()`, so the handler itself cannot become the crash) |
| the crash could not be attributed (the owner check itself failed) | still JSON, but treated as a stranger: `crashReportMinimal()` answers the same generic `internal` body — details only under `PANEL_DIAG=1` |
| a script that fails to **parse or load** (truncated paste, bad build) | 1101 on every route — nothing inside the file can catch that; this is what the size/marker checks, the app's `pasteScriptIsSane()` gate and the Workers Builds path exist for |
| a throw in **global scope** while the module evaluates, or a fatal runtime kill (out of memory / CPU limit) | 1101 (or 1102 for CPU) — the isolate never ran our `catch` |
| a **deploy the API refused** (invalid config/binding, size limit, token scope) | nothing is deployed: the deploy log shows the error and either the old version keeps serving or the broken one keeps returning 1101 |
| an error thrown while a response body is already streaming, or inside `ctx.waitUntil()` / after a WebSocket upgrade | the response is already sent; the error is recorded and shows up in `/api/diag` (`recentErrors`) |

`/api/diag` (owner-only) is the other half of the story: it lists the bindings this
isolate sees, runs a real KV write→read→delete probe, and shows the last crashes.
Together with `/api/selfcheck` you can tell «the panel is broken» from «the request
was broken» without guessing.

If you see the report, send it (minus anything private) — it names the exact line.
If you see 1101 *without* the report, the deployment itself is the problem, and the
fix is a redeploy: Cloudflare Dashboard → Workers & Pages → your Worker → Deployments,
or connect the repo under **Settings → Builds** (see above) so the file is read from
GitHub instead of copied by hand.

**Clean IPs (ایپی تمیز) — scanned on the device, not in the worker**

- Panel → 📡 tab → *Scan with Cat Client* opens the app scanner
  (`catclient://scan?sni=<host>`); paste the winners back into the panel (or any
  list from ircf / CFScanner). They go first in every subscription.
- `CF_IPS` env adds more addresses; the built-in default list is appended after
  yours (toggle in settings).

**Stable exit IP / country (v6.1) — "خروجی ثابت"**

Cloudflare egress differs per colo and per proxy-IP relay, so IP-check sites may
show a different country each time you reconnect. Two fixes, both built in:

- **Chain outbound** (like BPB *chain proxy* / Zeus *آی‌پی ثابت*): Settings →
  *Fixed exit* → `socks5://user:pass@host:port` or `http://host:port` pointing at
  a server you own. The worker opens every TCP connection through it, so the exit
  IP never changes. Mode `all` chains everything; `cf` only replaces the proxy-IP
  hop for Cloudflare-hosted sites. *Strict* refuses to fall back to a direct dial.
  `🧪 Test chain` → `POST /api/chain-test` dials once through the relay.
- **Pin one entry address** so the client cannot hop between Cloudflare edges:
  `/sub/<uuid>?addr=<ip-or-host>&limit=1` (also `?port=`, `?proto=vless|trojan`,
  `?limit=N`; works for `/clash` and `/singbox`). Clash's selector now defaults to
  the first concrete proxy with `⚡ Auto` as a `fallback` group; sing-box's selector
  defaults to the first outbound. Pick one server in V2Box instead of "Auto".

**Countries (v6.2) — pick an exit country, auto-fallback only when it is dead**

- Tag each entry address with the country it lands in *for you*: paste
  `ip#DE` lines (the Cat Client scanner reads the colo from `/cdn-cgi/trace`) or
  use the flag menu next to each ip in 📡 → *Countries*. `CF_IPS` accepts the same
  `ip#CC` form. Config names start with the flag, so every client groups them.
- Click a country → it becomes the preferred exit: its entries come first in
  `/sub`, Clash gets a `url-test` group per country and a root **`fallback`**
  group `[🇩🇪 Germany, ⚡ Auto]` (stays in Germany while any German ip answers,
  otherwise the fastest other country), sing-box's selector defaults to that
  country's `urltest`. *Fallback = never* keeps only that country.
- `?country=DE` (`&strict=1` for that country only) works on every sub URL.
- `🌍 Detect proxy-IP countries` tags the proxy ips (`POST /api/proxy-geo`); the
  preferred country's proxy ip is tried first for Cloudflare-hosted sites.
- `GET /api/colo` (public, free) tells a client which colo/country it reached.
- Cat Client app: when the chosen location has no live server at start, it now
  connects via Automatic and shows a notice instead of failing; the choice is kept.

**Routing, fragment & full-Xray output (v6.3)**

- Settings → *Routing*: **Iranian sites/apps direct** (default on — banking,

### 🔗 Quick links (`?p=`) — cookie in, URL out

The panel appends `?p=<password|uuid>` when the app opens it (and old bookmarks use
the same trick). Since 6.67.0 that value is turned into a session cookie and
**removed from the URL — on success and on failure**. Before, a *failed* attempt
kept the value in place, so the master UUID (or a typo'd password) stayed in the
address bar, in the browser history and in the `Referer` of everything the page
loaded afterwards. A failed quick link now redirects once with `?stale=1`, a flag
with no value in it, and the login page explains that the link no longer works
(because the password or the UUID changed) before stripping the flag as well. A
`?p=` link only works while the panel password is still the UUID — after you set a
password, sign in with it.
