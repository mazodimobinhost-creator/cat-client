# 🚀 ربات دیپلوی مستقل (Cat Deploy Bot)

این ربات فقط پنل Cat را روی حساب Cloudflare خودت نصب/به‌روزرسانی می‌کند؛ با ربات داخل پنل که مدیریت کاربران و subscriptionها را انجام می‌دهد فرق دارد.

```text
Telegram /deploy
  → بررسی secret پایدار PANEL_UUID (نباشد → راهنما و توقف، بدون تماس با کلادفلر)
  → دریافت آخرین release پنل از GitHub
  → بررسی bindingهای نصب فعلی و حفظ KV/تنظیمات + اعمال PANEL_UUID به‌عنوان binding UUID
  → آپلود Worker با دسترسی پنل و subscription بسته به‌صورت پیش‌فرض
  → بررسی /health و تطبیق نسخهٔ پاسخ‌داده‌شده
  → ارسال نتیجه و اطلاعات لازم فقط به گفت‌وگوی خصوصی ادمین
```

توکن Cloudflare ربات فقط در **Worker Secrets خودت** می‌ماند؛ داخل چت یا مخزن قرار نمی‌گیرد. فقط شناسهٔ تلگرام تنظیم‌شده در `TG_ADMIN_ID` مجاز است فرمان اجرا کند. برای جلوگیری از افشای UUID و لینک subscription، فرمان‌ها باید در گفت‌وگوی خصوصی با ربات فرستاده شوند و پاسخ `/deploy` نیز با قابلیت محافظت محتوای تلگرام ارسال می‌شود. بااین‌حال، UUID و لینک subscription را همچنان محرمانه نگه دار.

## قدم ۱ — استقرار خود ربات

**راه راحت — دکمه:**

> [![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/mazodimobinhost-creator/cat-client/tree/main/deploy-bot)

**یا دستی:** Cloudflare → Workers → Create → Worker (`cat-deploy-bot`) → Quick edit → محتوای `deploy-bot/worker.js` را paste کن → Deploy.

## قدم ۲ — افزودن Secrets

در Workers → `cat-deploy-bot` → **Settings → Variables & Secrets**، این پنج مقدار را از نوع **Secret** اضافه کن:

| نام | مقدار |
|---|---|
| `TG_TOKEN` | توکن ربات از @BotFather |
| `CF_API_TOKEN` | توکن Cloudflare با Workers Scripts: Edit و Workers KV Storage: Edit |
| `CF_ACCOUNT_ID` | شناسهٔ حساب Cloudflare |
| `TG_ADMIN_ID` | شناسهٔ عددی تلگرام ادمین |
| `PANEL_UUID` | UUID پایدار پنل — یک‌بار بساز و دیگر تغییرش نده |

اختیاری: `WORKER_NAME` (پیش‌فرض `cat-panel`) و `GH_REPO` (پیش‌فرض `mazodimobinhost-creator/cat-client`).

`PANEL_UUID` را **محلی روی دستگاه خودت** بساز و همان‌جا نگه دار؛ ربات آن را هر بار به‌عنوان binding سازگار `UUID` به Worker پنل می‌دهد، پس با هر دیپلوی دوباره تغییر نمی‌کند و لینک subscriptionها ثابت می‌ماند:

```bash
node -e "console.log(require('node:crypto').randomUUID())"
```

> ⚠️ اگر این secret را بعداً عوض کنی یا پاک کنی، UUID پنل و لینک‌های `/sub/<uuid>` تغییر می‌کنند. مقدار فعلی را قبل از هر تغییر یادداشت کن.

## قدم ۳ — ثبت webhook تلگرام

مسیر `/register` به کلید تأییدی نیاز دارد: ۱۶ رقم نخست SHA-256 توکن تلگرام. هش را **محلی روی دستگاه خودت** حساب کن؛ توکن را به سایت آنلاینِ هش‌ساز نده. نمونه در Bash:

```bash
read -s TG_TOKEN
export TG_TOKEN
node -e 'const c=require("node:crypto"); console.log(c.createHash("sha256").update(process.env.TG_TOKEN).digest("hex").slice(0,16))'
unset TG_TOKEN
```

بعد در مرورگر، آدرس Worker ربات را با این مسیر باز کن:

```text
/register?key=<هش-۱۶-رقمی>
```

اگر پاسخ `webhook registered` بود، ربات آماده است. خود توکن را در URL، چت تلگرام، issue یا log قرار نده.

## قدم ۴ — استقرار پنل

در گفت‌وگوی خصوصی با ربات:

- `/deploy` — آخرین release را نصب/به‌روزرسانی می‌کند
- `/deploy <branch>` — نسخهٔ شاخهٔ مشخص را برای آزمایش می‌گیرد؛ برای استفادهٔ عادی از release استفاده کن
- `/doctor` — وضعیت حساب، Worker، KV و health را گزارش می‌کند
- `/save` — نسخهٔ ذخیره‌شده در تاریخچهٔ Cloudflare و نام bindingهای قابل‌بازیابی را گزارش می‌کند؛ مقدار Secretها هرگز نمایش داده نمی‌شود
- `/repair` یا `/heal` — فقط پس از شکست واقعی `/health` نسخهٔ معتبر را دوباره deploy و بررسی می‌کند؛ اگر نسخهٔ تازه هم سالم نشود، به نسخهٔ قبلی برمی‌گردد
- `/rollback` — برگشت دستی به نسخهٔ قبلی
- `/status` — وضعیت توکن و Workerها

## خودترمیم و ذخیرهٔ پروژه

خودِ Cloudflare هر deploy را در **Version history** ذخیره می‌کند؛ بنابراین `/save` فایل یا توکن را در تلگرام کپی نمی‌کند و فقط نسخه و bindingهای بازیابی‌پذیر را تأیید می‌کند. در update و repair، bindingهای KV و D1 مثل `IOT_DB`، UUID و bindingهای خواندنی دوباره متصل می‌شوند و مقدار Secretها با `keep_secrets` در سمت Cloudflare حفظ می‌شود.

Cron ربات هر ۱۰ دقیقه `/health` را بررسی می‌کند. اگر سالم باشد مطلقاً چیزی deploy نمی‌کند. اگر در یک دور به تعداد آستانه (پیش‌فرض دو بار) پشت‌سرهم خراب باشد، همان مسیر امن `/repair` اجرا می‌شود: خواندن تنظیمات فعلی → دریافت release معتبر → deploy با bindingهای حفظ‌شده → تأیید دوبارهٔ health → rollback در صورت شکست. نتیجهٔ اقدام به گفت‌وگوی خصوصی ادمین فرستاده می‌شود. برای خاموش‌کردن این رفتار، متغیر `AUTO_HEAL=0` را روی Worker ربات قرار بده. `HEAL_FAILURE_THRESHOLD` فقط ۲ یا ۳ پذیرفته می‌شود. با `SAFE_REF` نیز می‌توان شاخهٔ محافظت‌شدهٔ بازیابی را تعیین کرد؛ در حالت عادی آخرین release استفاده می‌شود.

این قابلیت 1101 ناشی از syntax/global-scope/broken deployment را با **redeploy** درمان می‌کند؛ تضمینی برای رفع محدودیت حساب، توکن نامعتبر، خطای CPU 1102 یا قطعی خود Cloudflare نیست.

## رفتار امنیتی و حفظ داده‌ها

- نصب تازه با `OPEN_PANEL=false` و `OPEN_SUB=false` بالا می‌آید؛ صفحهٔ پنل و subscription ریشه به‌صورت عمومی باز نیستند.
- ربات **هیچ UUID تصادفی نمی‌سازد**. مقدار secret پایدار `PANEL_UUID` منبع حقیقت است و با هر دیپلوی به‌عنوان binding سازگار `UUID` روی Worker پنل نوشته می‌شود. رمز اولیهٔ پنل همان UUID است و ربات آن را در پاسخ خصوصی `/deploy` نشان می‌دهد؛ بعد از ورود، رمز دلخواه تنظیم کن. لینک subscription اصلی نیز شامل همین UUID است.
- هنگام به‌روزرسانی، UUID و binding واقعی `CAT_KV` حفظ می‌شوند. bindingهای خواندنی دیگر هم منتقل می‌شوند و secretهای قبلی با سازوکار `keep_secrets` حفظ می‌شوند، بدون اینکه مقدار secret خوانده یا در پاسخ چاپ شود.
- **مهاجرت از نسخهٔ قدیمی همین ربات:** نسخهٔ قدیمی UUID صریح نمی‌نوشت و پنل/ساب را باز می‌گذاشت. اولین deploy بعد از این تغییر، مقدار `PANEL_UUID` را روی Worker می‌نشاند و دسترسی عمومی را می‌بندد؛ اگر UUID قبلی خالی یا متفاوت بود، ربات هشدار می‌دهد که لینک‌های اشتراک قبلی عوض می‌شوند و باید لینک جدید را وارد کنی. بعد از آن تا وقتی secret ثابت بماند، UUID در updateهای بعدی ثابت می‌ماند. اگر رمز را قبلاً داخل پنل عوض کرده‌ای، مقدار hashشده در KV می‌ماند و باید همان رمز قبلی را استفاده کنی؛ اگر عوض نکرده بودی، `PANEL_UUID` رمز پیش‌فرض است.
- اگر `PANEL_UUID` نباشد یا معتبر نباشد، ربات **قبل از هر فراخوانی Cloudflare** متوقف می‌شود و در پاسخ `/deploy` و `/setup` دقیقاً می‌گوید چه چیزی کم است. ربات هرگز برای پرکردن این خلأ UUID تصادفی نمی‌سازد، چون ساختن UUID تازه در زمان دیپلوی لینک‌های اشتراک موجود را بی‌سر و صدا می‌شکند.
- اگر خواندن تنظیمات Worker فعلی شکست بخورد، ربات **قبل از آپلود متوقف می‌شود** تا هویت، KV یا bindingهای موجود را ناخواسته از بین نبرد.
- اگر `OPEN_PANEL` یا `OPEN_SUB` به‌شکل secret binding تنظیم شده باشد، ربات به‌روزرسانی را متوقف می‌کند؛ آن binding غیرمعمول را در داشبورد Cloudflare بررسی و اصلاح کن.
- آپلود موفق به‌تنهایی به معنی آماده‌بودن نیست. پاسخ «تأیید نشد» یعنی `/health` همان نسخه را تأیید نکرده؛ ربات خودش rollback نمی‌کند. `/doctor` را اجرا کن و در صورت لزوم `/rollback` بزن.
- پیام‌های `/deploy` محافظت‌شده‌اند تا در Telegram به‌سادگی فوروارد/ذخیره نشوند؛ این جای امن نگه‌داشتن حساب تلگرام را نمی‌گیرد. اگر توکن ربات لو رفت، در BotFather آن را revoke کن و Secret را عوض کن.
