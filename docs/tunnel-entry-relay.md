# تانل‌کردنِ IP ایران و IP خارجیِ کلودفلر — چه چیزی الان هست، چه چیزی کم است

پاسخِ کوتاه: **بله می‌شود** — و زیرساختِ زنجیره در اپ از قبل هست
(`ConnectionChain.kt`). چیزی که کم است این است که «استفاده به‌عنوان entry» در
اسکنرِ ProxyIP **فقط** یک fronting-IP می‌سازد و **زنجیرهٔ صریحِ entry ↔ relay را
از UI نمی‌سازد**. این سند سؤال را جواب می‌دهد و مسیرِ افزودنِ «بخش» را با
انتخاب‌هایی که باید بگیری روشن می‌کند.

---

## ۰) سؤال دو-قسمتی بود؛ پس دو جوابِ جدا دارد

| چیزی که پرسیدی | جواب |
| --- | --- |
| IP **ایران** را تانل کنم؟ | ✔ شدنی. ایران = زنجیرهٔ داخلی (ایران → خارج). فقط باید **معنای نقشِ** آن IP را روشن کنی: «ورودیِ محلی/کارت» یا «هوپ میانی». |
| IP **خارجیِ کلودفلر که از پروکسی‌IP به دست می‌آید** را تانل کنم؟ | ✔ شدنی، ولی اینجا «تانل» یعنی **fronting روی آن IP** — عملاً کاری که الان «استفاده به‌عنوان entry» نصفه انجامش می‌دهد. کلیدِ ماجرا: ProxyIP خودش **ورودی** نیست، **مقصد** است (پروکسیِ هاستِ مقصد). |

نکتهٔ ظریفی که خیلی‌ها را گمراه می‌کند: در ذهنِ کاربر «ProxyIP = یک IP برای تانل»
است؛ در کد، ProxyIP یعنی «به‌جای اینکه SNI را به دامنهٔ اصلی بزنیم، آن را به این
IP بزنیم». پس اگر آن IP را در زنجیره بگذاری، نقشش **پیوندِ آخر** است، نه **پیوندِ
اول**. هر جای دیگری بگذاری‌اش، یا بی‌اثر است یا خودش را دور می‌زند.

---

## ۱) چهار نوع IP که در همین اپ کنارِ هم قاطی می‌شوند

این‌ها را از هم جدا کن، وگرنه هر بحثی در مورد «تانل» به آشفتگی می‌رسد:

| نوع | چه کاری می‌کند | در اپ |
| --- | --- | --- |
| **ورودیِ ایران** (IP سرورِ ایران) | کاربر به این وصل می‌شود؛ اگر IP مستقیم بلاک باشد، **fronting** می‌شود (روی SNI یا IP سالمِ جلویی می‌نشیند) | `frontingIps` + SNI |
| **هوپ میانی/relay** | مسیر را دو تکه می‌کند: ایران → میانی → مقصد (عبور از بلاکِ مسیر) | `ConnectionChain` (hop/slots) |
| **ProxyIP** | جای IP دامنهٔ **مقصد** می‌نشیند (`host:port` یا ارجاع به کانفیگ) | ProxyIP scanner/sub |
| **خروجی/کشور** | برای انتخابِ مسیر و نمایشِ کشور در UI | `RelayCountryLookup`، `ProxyEgressCountry` |

تانل یعنی تو عمداً دوتای اول را با هم ترکیب می‌کنی. کاری که الان از UI ممکن است،
ترکیبِ سوم با اول است (و فقط به‌شکلِ «fronting»).

## ۲) گزینه‌های واقعی برای «بخشِ تانل» — از ارزان به گران

### گزینه A — یک تعمیرِ کوچک، بدونِ UI (نصفِ روز)
`applyProxyIpAsEntry` امروز فقط `frontingIps += ip` می‌کند. تفاوتش با آنچه تو
می‌خواهی در یک چیز است: آن مسیر به `saveFrontingIps(reconnectIfChanged = true)`
می‌رسد و **SLOT/Via را پاک نمی‌کند**. اگر زنجیره‌ای در جریان باشد، fronting و
زنجیره می‌توانند هم‌زمان فعال بمانند و رفتارِ نتیجه غیرقابلِ پیش‌بینی شود.

اصلاح: در `applyProxyIpAsEntry`، اگر `ConnectionChainSettings` خالی نیست، از کاربر
یک سؤالِ بله/خیر بپرس («زنجیرهٔ فعلی پاک شود؟ / به‌عنوان هوپ اضافه شود؟») و **یکی را
قطعی کن**. این ارزان‌ترین کاری است که جلوی باگِ «تنظیماتِ روی هم افتاده» را می‌گیرد.

### گزینه B — بخشِ کامل (پیشنهادِ من)
یک صفحهٔ «تانل» با دو نقشِ صریح، دو-سه ردیف، بدونِ هیچ کتابخانهٔ بیرونی:

```
ورودی   (entry)   : [ انتخاب از: ایران / لیست fronting / Custom ]  → SNI: [...]
مسیر    (hops)    : [ + افزودن هوپ ]  ← هر هوپ: type (relay/config/proxyip) + addr
پیوندِ آخر (exit)  : [ ProxyIP: host:port یا از اشتراک ]   [x] استفاده
```

نقشهٔ فنی که همه‌اش در درخت هست:
- `ConnectionChain.kt`: `ConnectionChainSlot/HopMode/ProfileRef/Hop`،
  `withHop`، `normalized`، `MihomoProxyBlock.render(runtimeName, dialerProxy)`، `parse`،
  `ResolvedConnectionChain*`، `ConnectionChainRuntimePlan` — استفادهٔ مجدد، بدونِ
  مدلِ جدیدِ داده.
- `ProxyIpScannerPage.kt:61` (`onUseAsEntry`) ⇒ دکمه‌اش از «افزودن به fronting»
  به «افزودن به‌عنوان هوپ / ورودی» تغییر می‌کند و رفتارش از `MainActivity.kt:10245`
  (که امروز `applyProxyIpAsEntry` است) عبور می‌کند.
- ساختِ کانفیگِ نهایی همان‌جایی است که خودش هست؛ فقط `render(runtimeName, dialerProxy)`
  با لیستِ هوپ‌های غیرخالی صدا زده می‌شود.

### گزینه C — بخشِ پنل (کارِ بیشتر، ارزشِ بیشتر برای دیپلوی)
پنل سمتِ ورکر مسیرهای `tunnelPaths/tunnelAuth` را از قبل دارد. اگر بخواهی «تانل»
از پنل کنترل شود (نه از اپ)، این مسیرها به `/ws` وصل می‌شوند و ورکر فقط نقشِ
هماهنگ‌کننده/کانال را بازی می‌کند. توجیهش فقط وقتی است که بخواهی بدونِ آپدیتِ APK
قواعدِ تانل را عوض کنی.

**هزینهٔ هر سه:** نمی‌توانم بدونِ دیدنِ کدِ `ConnectionChain` (که دیده‌ام) و بدون
انتخابِ تو، ساعت بزنم؛ ولی A حدوداً یک نشست است، B چند نشست (UI + تست + بازتولیدِ
آرتیفکت)، C بیشتر.

## ۳) خطرهایی که تانل را در این اکوسیستم بی‌اثر می‌کنند (قبل از کدنویسی بخوان)

1. **ProxyIP را وسطِ زنجیره نگذار** — آن IP برای «هاستِ مقصد» است. اگر هم
   entry و هم ProxyIP یک IP شوند، مسیر خودش را می‌بندد.
2. **SNI و Host را همراستا کن** — fronting یعنی دامنهٔ SNI با دامنهٔ مقصد یکی نیست؛
   بعضی نودها ۴۲۱ می‌دهند. مسیرِ سالم: SNI = دامنهٔ خودت (یا دامنهٔ سالمِ مجاز)،
   Host = همان، و **ProxyIP = IP**. این ترکیب در اپ پشتیبانی می‌شود.
3. **نقشهٔ کشور و پینگِ دیتاپلین** — با هر هوپِ اضافه، پینگِ نمایشی که
   `RelayCountryLookup/ProxyEgressCountry` حساب می‌کند **حداقلِ** مسیر نیست؛ الان
   عدد را از نودِ انتخاب‌شده می‌گیرد. اگر تانل اضافه شود باید مشخص شود کدام عدد
   نمایش داده می‌شود (پینگِ ورودی یا خروجی) — وگرنه دوباره می‌رسیم به
   «کشور را نشان نمی‌دهد».
4. **کلودفلر ۱۱۰۱ هم اینجا هست** — اگر ورکر بین راه بمیرد، خطا در `fetch()` **پرتاب
   می‌شود** (رفتارِ service bindings / dynamic dispatch) و قابلِ catch است. پس
   زنجیره‌ای که ورکر در آن هست، بهتر از زنجیرهٔ خالصِ TCP خطا می‌دهد، نه بدتر.
5. **یک خطِ ممنوعه:** IP سرورِ شخصیِ خودت را در سورسِ گیت/ریلیز نگذار (همان
   قاعدهٔ همیشگی: توکن/آدرسِ سرور کامیت نشود).

---

## ۴) دو بیت‌عارفی که باید جواب بدهی تا شروع کنم

1. **سطح:** این بخش در **اپ** باشد (گزینه A/B: کاربر موبایل، سریع، اما هر تغییر
   نیازِ آپدیتِ APK دارد) یا در **پنل/ورکر** (گزینه C: از راه دور کنترل می‌شود،
   ولی مسیرهای `tunnelPaths/tunnelAuth` را باید به `/ws` وصل کرد)؟
2. **رفتارِ پیش‌فرض:** وقتی زنجیره‌ای فعال است و کاربر از اسکنر ProxyIP روی
   «استفاده به‌عنوان entry» می‌زند، کدام پیش‌فرض باشد: **(الف)** زنجیره حفظ شود و
   IP به‌عنوان **هوپ** اضافه شود، یا **(ب)** IP فقط fronting شود و **زنجیره پاک
   شود**؟

جوابِ این دو + یک مثالِ واقعیِ سناریو («می‌خواهم X وصل شود به Y و بعد به Z، چون
مشکلِ من ... است») کافی است تا وصله/بخش را بزنم. بدونِ این‌ها هر پیاده‌سازی‌ای
حدس است و بعداً باید دوباره بازش کنیم.
