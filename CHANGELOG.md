## [1.10.0-beta181] — 2026-10-27 (Panel 6.69.39)

### Fixed
- **HTTPUpgrade configs never connected (all servers, not only Vercel):** Mihomo has no `network: httpupgrade`; an unknown network silently falls back to plain TCP+TLS, so every imported `type=httpupgrade` link (share link, sing-box JSON, Xray JSON, app subscriptions) produced a proxy that could never work. Converted proxies now use Mihomo's real shape — `network: ws` + `ws-opts.v2ray-http-upgrade: true` (early data → `v2ray-http-upgrade-fast-open`) — through one normaliser (`SubConvConverter.normalizeMihomoTransport`) plus the sing-box / Xray paths in `UserSubscriptions`. Export back to a share link keeps `type=httpupgrade`. Checked against the Mihomo v1.19.30 source the app ships; new regression test in `MihomoShareLinkTest`.

### Added
- **Play Protect explained in the updater:** a plain-language note under the update panel says what «App scan recommended» means (it appears for every new APK Google hasn't seen; it is not an error) and what each button does («Scan app», «Install without scanning», «Don't install app»). The app cannot suppress that Android dialog.
- **`scripts/panels/vercel-transport.test.mjs`** (13 checks, in `npm test` and CI on the shipped panel): the real Vercel adapter + panel carry VLESS/Trojan over WebSocket end to end; the Vercel subscription (links, Clash, sing-box) stays WebSocket-only; an httpupgrade client is refused at once instead of hanging.

### Verified live (not shipped as a feature)
- **HTTPUpgrade cannot run on a Vercel Function:** a probe deployed on Vercel (iad1) showed that the edge answers `101` for a key-less httpupgrade request but then forwards **only valid WebSocket frames** — raw bytes after 101 never arrive in either direction (project domain and 216.198.79.65 alike), while real WebSocket echoed in 51–484 ms. So the Cat panel on Vercel keeps WebSocket only, and no httpupgrade twins are generated (they would import and never connect). The probe project was deleted.

- **App 1.10.0-beta110 (4/4) — the multi-path watchdog: the path changes by itself, but never because of one bad minute.** With three paths in the app (our edge, Orbot/Tor, the emergency DNS-tunnel bridge) the remaining question is not «which one is best» but *when* to stop insisting on the normal one — and the obvious rule, «it failed, switch», is the wrong one: a single dead clean IP or a carrier hiccup would throw the owner onto a slow Tor path, and the first success would yank them back, so the connection would change shape every minute. Four rules were chosen instead of the naive trigger: **(1) a run, not an event** — the primary has to fail **twice in a row** before the fallback is used, and **one success resets the run to zero**, so a path that recovers is not punished for its past; **(2) the fallback is temporary** — after **10 minutes** the normal path gets one more try, and if it fails again the run rebuilds and Tor takes over again (that is what makes «stays connected» honest instead of «stuck on Tor forever»); **(3) a fallback that does not answer is not a fallback** — with Orbot closed the watchdog stays on the primary and says so, instead of routing into a dead local port; **(4) the outcome counted is the *primary* one** — an attempt that rode Orbot says nothing about whether the normal path works, and counting it would make the watchdog forget it had taken the fallback at all. The switch lives in the same settings row as the Orbot engine, in both languages, with a verdict line that states the run it is actually on («2 consecutive failures of 2» / «currently on Tor; in 10 minutes the normal path is tried once more» / off), and the state (armed, failure run, on-fallback, since when) survives a process restart because a watchdog that forgot it was on the fallback would crawl back to a path that is known to be dead. *(Verified, two halves and labelled: **behaviour** — `app/src/test/java/com/cat/client/PathWatchdogTest.kt`, 12 JVM tests run by the Android CI job against the real policy object: one failure is noise, the threshold switches, one success resets, the switch records when it started and clears the run, the retry window is respected to the millisecond and expires at its edge, a vanished fallback returns immediately, a return cannot be bounced back by the old failures, «no fallback» and «disarmed» are hard never-move rules, and the status line names the run; **wiring** — 18 more executed checks in `scripts/panels/orbot-engine.test.mjs` (the file is at **53/53** with them), which assert the probe-before-activate rule on the real service source: the probe result must be followed by `return null` (the normal path) before any hop, the outcome is recorded around the attempt itself, an Orbot attempt is excluded from the run, that probe is wrapped in `withContext(Dispatchers.IO)` and skipped entirely when neither half can act, both switches and all five strings exist in en + fa with matching placeholders (checked by reading them back out of the XML). - **App 1.10.0-beta110 (1/4) — the encrypted-DNS picker learned the two QUIC transports, because ECH is only as good as the lookup that fetches its key.** The DNS section could already pin DoH or DoT, and the connection-details line already reported ECH (`ECH enabled/disabled/not applicable/unknown`), but the half that decides whether ECH can work *at all* was missing: the ECH key rides in the zone's HTTPS/SVCB record, so the lookup is the whole game — if plaintext DNS is poisoned or the encrypted resolver is blocked, the key never arrives and `ech-opts` has nothing to use. Iran has repeatedly blocked external DoH/DoT resolvers (recorded with sources in [`docs/iran-2026-notes.md`](docs/iran-2026-notes.md)), while its middleboxes do not parse QUIC. So the picker gained **DoQ (`quic://`, port 853)** and **DoH3 (`h3://`)** as first-class modes, each with its own stored endpoint, its own hint/helper text in both languages, and a default that is a bare **IP** (`quic://1.1.1.1:853`, `h3://1.1.1.1/dns-query`) precisely so no plaintext lookup has to succeed first. - **App 1.10.0-beta110 (3/4) — the Orbot / Tor engine: a path that depends on nothing of ours.** Every other path in the app ends at *our* edge or at a subscription, so when that edge is blocked as a whole there is nothing left to dial. Orbot runs Tor on the phone itself and exposes a SOCKS5 listener on loopback, so the app can make the whole runtime go out through `127.0.0.1:9050` — and it does not need to know which pluggable transport Orbot used, which is the point: the owner can change that inside Orbot (WebTunnel today, dnstt tomorrow) without touching the app. Four decisions were made rather than defaulted: **(1) loopback only** — the normalizer refuses any address that is not `127.0.0.0/8` or `::1`, because a "127.0.0.1" that is not loopback would quietly hand the exit to a stranger; **(2) the outbound is a real proxy block** injected into the config the core reads (`socks5`, `udp: false` — Tor's SOCKS5 carries no UDP, and claiming UDP would make QUIC look tunneled while it is dropped), inserted into the existing `proxies:` list and *replacing* an entry of the same name so a runtime that is rebuilt on every reconnect cannot grow a second copy; **(3) the routing shape is forced, not suggested** — while the engine is on, the effective routing mode becomes the global-proxy shape, the subscription's own rules are dropped (a `DOMAIN,…,DIRECT` rule would be a hole in the tunnel) and the encrypted DNS resolvers are pinned to the same proxy (`#cat-orbot`), so no lookup leaks around Tor;
