## [1.10.0-beta226] — 2026-10-29 (Panel 6.79.1)

### Fixed — linked panels (KataBump ⇄ Cloudflare) and every VLESS/Trojan chain exit
- **The chain never reached a Node panel.** Three wire bugs, found with a new real-socket test (real launcher process + Cloudflare panel), meant «exit through the linked panel» and every VLESS/Trojan chain to a Node/Vercel/KataBump panel could not carry a byte:
  1. the WebSocket client key was 24 random characters instead of base64 of 16 bytes — Node's `ws` (all Node hosts) answered `400` to the upgrade;
  2. the VLESS request had no «addons length» byte, so a real VLESS server (Xray or our panel) read the command as the port and refused it;
  3. the dialer waited for the server's first answer before letting the phone send — but VLESS servers only answer with the first target data and Trojan servers never answer, so every chained connection hung until its timeout. It now returns at once and strips the 2-byte VLESS answer when it arrives.
- Proven end to end: phone → Cloudflare panel → (sockets) → KataBump launcher on one port → target, both the source and the minified artifact.

### Added — server country per host
- **Railway: «📍 Server country» picker** (Amsterdam — recommended for Iran, Virginia, California, Singapore). The app sets it through `serviceInstanceUpdate` / `multiRegionConfig` right after creating the service (step 4/8); if Railway refuses, the install continues on the account's preferred region with a clear note. The saved panel name carries the flag.
- **Bot-Hosting:** the country cannot be chosen (their rules); after install the app shows the real node and its country (fi / de / us / fr / eu).
- Guides now state each host's rule: KataBump France only (OVH Gravelines), Lucity EU only (PORT 8080 automatic, «Generate Domain» needed), Shiprr region eu / us / asia / oc at app creation (a preference, may fall back), SmarterASP Europe (Amsterdam) or USA at sign-up.

## [1.10.0-beta223] — 2026-10-29 (Panel 6.78.0)

### Added — app (Xray engine)
- **The real Xray-core is now inside the app, for the configs the Cat core cannot run as written.** The official XTLS/Xray-core (MPL-2.0, v26.10.21, pinned commit `1b1647c`) is compiled unmodified from source in CI (`scripts/build-xray-core.sh`) together with a small Cat runner (`scripts/xray-runner/main.go`) and shipped as `libxray.so` for arm64-v8a, armeabi-v7a, x86 and x86_64.
- Configs with `finalMask` (the Irancell «F&F» method, e.g. `fm=tlshello-0-len`) are carried by Xray automatically: each one gets its own `127.0.0.1` SOCKS inbound and the Cat core sees a local SOCKS entry with **the same name**, so groups, the location list, latency tests and route memory work unchanged. Xray dials the server with the original VLESS / Trojan / VMess settings (TLS or REALITY, ws / httpupgrade / xhttp / grpc / raw, SNI, ALPN, fingerprint incl. `unsafe`, `cipherSuites` passed through) **plus a real `finalmask`**: `tlshello-0-len` = split the TLS ClientHello into TLS records of 100–200 bytes written at once; `tlshello-<delay>-<length>`, packet ranges (`1-3` for REALITY), Xray JSON `{"tcp":[…]}` and the legacy `{"fragment":{…}}` form are understood too.
- Everything else stays on the Cat core. Proxies Xray cannot take as-is (`skip-cert-verify` — Xray removed `allowInsecure` —, ECH, certificate pins, chained `dialer-proxy`) keep the beta221 path (fragmenting proxy).
- **No VPN loop:** the runner registers an Xray dialer controller that hands every new socket to the VPN service for `protect()` over a private unix socket (app-private directory, same-UID check). The runner exits when the app process dies (stdin watch); leftovers are killed by PID on the next start.
- **Fallback:** if Xray is not packaged, switched off or does not start, the same connect attempt is repeated on the beta221 path (log `xray.fallback.byeDpi`). Xray starts before the Cat core so its first health checks already find the local ports.
- «🧬 Real engine status» shows the Xray state and has an on/off button (default on). The firewall guide now says that F&F configs run on the built-in Xray core and that `semi-python` is not a real cipher name (Xray ignores it too).

### Verified
- The runner was built locally against Xray-core v26.10.21: the generated config (VLESS+ws+TLS F&F, Trojan+xhttp, VLESS+REALITY+Vision, VMess+grpc) passes `xray -test`; a live run protected the outbound socket through the unix socket and the ClientHello left as 11 TLS records (at most 194 bytes each); closing stdin stopped the runner.

### Tests
- `Beta223XrayEngineTest`: eligibility, YAML swap keeps names/groups, the full F&F outbound, `finalMask` forms, Xray fingerprint names, inline Trojan/xhttp entries, leftovers still go through ByeByeDPI, service order/fallback/stop wiring, pinned build + protect contract.

## [1.10.0-beta219] — 2026-10-29 (Panel 6.77.3)

### Fixed — app («connected, but nothing loads / Instagram freezes»)
- **Cat Warp: pages and Instagram hung after connecting.** The VPN interface always advertised MTU 1280, also for the two-hop transports whose inner hop only carries 1200 bytes (WARP-in-WARP, WireGuard-over-MASQUE) or 1162 (MASQUE-in-MASQUE) — the default for every «foreign exit» profile. Small packets passed, so it showed «connected», but every full-size packet was silently dropped, so pages, images and videos never finished. The interface now uses the transport's real size (from the config the engine actually runs, including after an automatic fallback); below 1280 it is IPv4-only, because Android refuses IPv6 on smaller interfaces (the same as the engine's own app).
- **Cat Fox VPN: after a few minutes nothing new opened.** The local bridge allowed only 64 connections and hung up on any further one; idle connections (which apps keep open for minutes) were never closed, so a normal phone filled all slots and every new connection — a new Instagram image, a new page — was refused. The limit is now 192, and when it is reached the connection that has been silent the longest (≥15 s) is closed for the new one.
- **Cat Fox VPN: one lost packet froze every app.** All connections shared one HTTP/2 connection to Mozilla; on a lossy mobile network one lost packet stalled everything at once. Busy phones now spread over up to 4 connections (24 tunnels each before another one is opened; a busy connection is still used while the next one is being dialled or if dialling fails). A dead connection is noticed faster (ping after 12 s of silence, 10 s to answer).
- **Cat Fox VPN: QUIC and DNS.** Mozilla's proxy carries only TCP to ports 80/443, so QUIC (UDP 443) went around the tunnel, straight into the filter, and apps like Instagram waited on it before falling back. For Cat Fox VPN profiles QUIC is now refused so apps use TCP at once, and DNS uses foreign DoH on port 443 only (DoT on 853, UDP DNS and the Iranian resolvers cannot work through a foreign web-only proxy). Other configs are unchanged.

### Tests
- `Beta219TunnelTrafficTest` (MTU per transport and for «foreign exit» configs, IPv6 only at ≥1280; tunnel-slot eviction of the idle tunnel, no permit leak; Cat Fox VPN runtime refuses QUIC before `MATCH` and uses DoH only; mixed subscriptions unchanged).

## [1.10.0-beta218] — 2026-10-29 (Panel 6.77.3)

### Fixed — app (connect froze the screen)
- **Pressing «Connect» froze the app.** The VPN service runs its startup steps on the main thread, which it shares with the screen. With the WARP → Psiphon (or WARP → Tor, or the two-hop WARP fallback) route, the Cat Warp carrier ran its blocking native preparation — endpoint scan, WARP provisioning and a «busy engine» retry that sleeps — right on that thread, so the screen stopped responding for seconds to minutes and even «Disconnect» could not be pressed. Validation and preparation (including both fallbacks) now run on a background thread; «Disconnect» works during the whole start and cancels a running preparation, and a failed preparation frees the carrier for the next try.
- **Smaller blocking steps moved off the screen's thread too:** the first load of the Cat Warp native library, writing the saved WARP key into the identity file, writing the Psiphon/Tor carrier config file, and stopping Cat DNS helper engines before a new start (a short wait per engine).

### Tests
- `Beta218ConnectFreezeTest` (no native validate/prepare left in the carrier's `start()`, preparation on IO, every carrier config write on IO, the service's native-library check and key file write on IO).

## [1.10.0-beta217] — 2026-10-29 (Panel 6.77.3)

### Fixed — app (speed)

## [1.10.0-beta216] — 2026-10-29 (Panel 6.77.3)

### Fixed — app (Cat Warp → Psiphon)
- **«failed to start Psiphon library … invalid tunnel protocol: FRONTED-MEEK-CDN-OSSH».** The Psiphon config of the WARP → Psiphon chain listed two tunnel protocols that do not exist in the bundled psiphon-tunnel-core 2.0.42 (`FRONTED-MEEK-CDN-OSSH`, `FRONTED-MEEK-CDN-HTTP-OSSH`), so the library rejected the whole config and every country (Germany, NL, US, …) fell straight to the two-hop WARP fallback — which exits in Iran, so the connection was (correctly) refused. - **Exit through the linked panel (real VLESS-WS chain).** Per link: *Off* / *Cloudflare sites only* / *All traffic*. «Cloudflare sites only» on a Cloudflare panel linked to Vercel/Railway opens Cloudflare-hosted sites through the other panel instead of a ProxyIP; «All traffic» gives every site the other panel’s IP (Vercel US / Railway fixed IP — e.g. for Gemini). A failed hop falls back to the normal route. Traffic that arrived over a link never leaves over a link again (no A→B→A loop). Cloudflare → Cloudflare exit is refused with an explanation (Workers cannot open sockets to Cloudflare addresses).
- **«🩺 Real check»**: the peer API answers with the shared secret (ms shown) **and** a tunnel through the peer reaches ip-api.com and reports the real exit IP + country. Nothing is assumed.
- **Combined subscription.** «➕ add this panel’s configs to my users’ subs»: every user’s sub link also carries the other panel’s configs (tagged 🔗, built by the other panel for its own host/ports, same user UUID). Users are mirrored there with only id + enabled + expiry (pushed on toggle, on «🔄 sync users», after every user change, and leased on each sub fetch for 45 days); a disabled or expired user stops working there too. Pinned/limited links (`?limit`, `?addr`) and Clash/sing-box/Xray-JSON outputs stay as they were.
- **Import from the linked panel**: «📥 ProxyIPs» / «📥 clean IPs» copy the other panel’s tested entries with **exactly** their ports (e.g. `103.237.102.191:11111`); SOCKS relays and credentials are never shared. Clean IPs move only between two Cloudflare-fronted panels.

## [1.10.0-beta187] — 2026-10-27 (Panel 6.69.43)

### Why Vercel configs do not ping from Iran (measured live from Vercel's edge, iad1)
- Vercel's edge only requires that **the certificate chosen by the SNI also covers the Host**. For a `*.vercel.app` project **any** vercel.app name works as SNI — even a made-up one (WebSocket 101) — and a custom domain works with its own name once Vercel has issued its certificate. `nextjs.org`, `react.dev`, `vercel.com`, `cursor.com` and every other foreign SNI get **421** for an ordinary project: the "react.dev / nextjs.org SNI" fronting trick from public configs only reaches Vercel's own and enterprise sites, never a personal panel. A custom domain without DNS/certificate also gets 421 with every SNI.
- So the blocks Iranian users hit are on the name: DPI on the vercel.app SNI, DNS poisoning of the project name, and (for some national-gateway IPs) Vercel's own DDoS shield answering 403 — which no config can bypass on a Hobby plan.

## [1.10.0-beta186] — 2026-10-27 (Panel 6.69.42)

### Fixed
- **Panel 6.69.42 — downloads losing bytes inside the tunnel (every panel since 6.41.0, Cloudflare and Vercel):** the downstream "grain bundling" loop raced each `reader.read()` against a 1 ms silence timer and threw the read away whenever the timer won; the next chunk then landed in that orphaned read and was lost. Whenever the site's packets arrived more than 1 ms apart — most real traffic — bytes vanished mid-stream: broken TLS, pages that stall half-loaded, videos and speed tests that die, configs that look "connected but nothing opens". Short answers (the old tests and pings) still passed, which is why it hid so long. The loop now keeps one outstanding read across the race. New regression test `tunnel-grain.test.mjs` drives the real `pumpTunnel` (also on the minified artifact in CI): before the fix 281,402 of 420,002 bytes arrived (gapped) and 54,052 of 105,842 (slow trickle); after it, every byte arrives in order.

### Added
- **Backpressure for slow clients (Vercel / Node):** while more than 2 MB is waiting for a slow phone (`ws.bufferedAmount`), the panel stops reading the site instead of buffering the whole download in the function's memory (one big download on a slow line could fill the instance and drop every connection on it). Cloudflare Workers report no `bufferedAmount`, so nothing changes there. Tested.
- **Vercel adapter, ideas from public Vercel panels found on GitHub (Behnam1323/Vercelfinal v4.6, LabourHour/deploy-vercel), written independently:** TCP keepalive on outgoing tunnels, a 5-minute DNS cache for tunnel destinations, a WebSocket ping every 25 s so mobile carriers do not drop a quiet tunnel (no pong is required, so nothing is cut), and `bufferedAmount` exposed to the panel for the backpressure above. `perMessageDeflate:false`, `TCP_NODELAY` and the pre-bind send queue were already in place.
